Ranking Signal Analysis: Prioritizing Content Fixes with FlyRank Data

Abstract

For content editors deciding which pages to fix first, we build a ranked priority score using FlyRank data to identify pages likely to lose clicks or under-perform. We derive time-aware labels from the FlyRank warehouse (prev30 vs next30 CTR) and create features using only data available before a chosen freeze date. We test simple rule baselines and a ranked model, validating on a time-aware holdout and reporting precision@K and average CTR lift. The analysis highlights the most predictive signals and produces a ranked action list with reason codes for editors. Results are presented as decision-support only, with limitations and reproducibility notes documented.

Introduction

This work supports editorial decisions: which content items should an editor prioritize to fix or refresh to prevent declines in search-driven engagement.

Data

  • Starter CSV: data/raw/content_refresh_anonymized.csv (30,000 rows) used for quick iteration.
  • Warehouse: hf://datasets/FlyRank/internship-warehouse — use fact_content_daily_performance_sample for iteration and fact_content_daily_performance for final scans.
  • Note: the starter CSV lacks a calendar report_date column suitable for time-aware labels; the warehouse provides daily rows required for honest future-window labels.

Methodology (overview)

  1. Choose freeze date T (example: 2026-05-01). Features use data <= T; labels use T+1..T+30.
  2. Aggregate per content_id × client_id: compute ctr_prev30 and ctr_next30 and form decline_label.
  3. Build features available at T (metadata, avg_position_prev30, ai_traffic_prev30, has_keywords, title_length, content_age_days).
  4. Baseline: rule-based score (position, CTR by type, missing keywords). Optional: simple ML model (LightGBM).
  5. Validation: time-aware holdout, per-client stability checks, and leakage tests (do NOT use derived trend columns as features).

Limitations

  • Panel bias: clients have different history depths.
  • Label noise: short windows and sparse data can lead to noisy labels.
  • Directional claims only: we provide decision-support, not causal claims.

Ranked recommendations (example)

  1. Top-decile items: prioritize metadata & title updates, add missing keywords, check content freshness.
  2. Use reason codes: low visibility (avg_position>10), low CTR for content type, no keywords present.
